## Суть приложения

Нужна система оформления заказов обуви «Чудо Обувь». Пользователь видит модели, выбирает доступный размер и количество, собирает заказ из нескольких позиций и подтверждает его. Система сохраняет заказ и пересчитывает остатки. Менеджер и администратор управляют заказами, администратор дополнительно меняет дату и удаляет отдельные позиции существующего заказа.

Это четыре последовательных этапа одного приложения. Модуль 5 независим: анализ отдельного набора CSV. Дальнейшая обработка заказа, доставка, оплата, полноценный учёт сети магазинов и аксессуары не входят в требуемую реализацию. Расширение ассортимента упомянуто как будущее развитие.

## Модуль 1 — база данных

Создать ER-диаграмму, PostgreSQL-базу, ограничения и связи, подготовить и импортировать пять файлов. Сохранить SQL-скрипт структуры С ДАННЫМИ. Один DDL без INSERT/дампа данных не выполняет требование.

Основные сущности, которые явно перечислены в 1.4: роли, пользователи, модели обуви, размеры, товарные позиции, заказы, позиции заказов. Вариант 3 в 1.4 демонстрирует подходящий минимальный состав семи сущностей; отдельные таблицы категорий/производителей могут быть удобны, но не обозначены как обязательное универсальное требование.

Рекомендуемый минимальный каркас:

| Таблица | Назначение |
| --- | --- |
| `roles` | Названия ролей |
| `users` | Фамилия, имя, отчество, уникальный логин, ссылка на роль |
| `products` | Категория, подкатегория, наименование, производство, изображение, описание, состав, базовая цена |
| `sizes` | Уникальное числовое значение размера |
| `stock_items` | Ссылка на модель, ссылка на размер, доступное количество; уникальна пара модель + размер |
| `orders` | Номер, дата заказа, ссылка на пользователя |
| `order_items` | Ссылка на заказ и товарную позицию либо модель + размер, количество, зафиксированная цена за единицу |

Третья нормальная форма означает здесь, например: не хранить весь заказ и все товары одной большой строкой; не делать поля `product_1`, `product_2`; роль не повторять текстом у каждого пользователя; данные модели не дублировать у каждой позиции заказа. Один заказ содержит много позиций. Итог вычисляется как сумма `quantity × unit_price`.

Названия всех таблиц и столбцов — латиницей в нижнем регистре, начинаются с буквы, содержат только буквы, цифры и `_`. Для Python использовать осмысленные идентификаторы и snake_case в подходящих местах; не писать несколько команд через `;` на одной строке. Неочевидную логику пояснять комментариями.

Типы: идентификаторы/количество — INTEGER; названия, ФИО, логин, путь — VARCHAR/TEXT; дата заказа — DATE; цена — NUMERIC/DECIMAL; размер тоже NUMERIC/DECIMAL, потому что есть 36.5 и другие половинные значения. Деньги в Python обрабатывать Decimal. Конкретные длина и точность в 1.5 не спрашиваются.

Рекомендуемые ограничения: PK и FK, уникальный логин, уникальный размер, уникальная пара модель + размер, количество остатка неотрицательное, количество заказа положительное, цены неотрицательные. При удалении заказа удаляются его позиции; каскадное удаление заказа не должно удалять модели и пользователей. Права дополнительно проверяются в логике операции.

Импортировать сначала справочники/роли, пользователей, модели и размеры, затем остатки, затем шапки и позиции заказов. Для исходных заказов одинаковый номер означает один заказ с несколькими строками состава. После импорта явных идентификаторов заказов проверить PostgreSQL sequence, чтобы новый заказ не получил уже существующий номер. Это техническая рекомендация, не отдельный пункт КИМ.

Конкретные расхождения:

1. Products, строка 18, столбец D: название «Туфли женские натуральная кожа с металлическими вставками» содержит неразрывный пробел U+00A0 перед «с». В Stock_Items (строки 50–53) и Orders (строка 9) обычный пробел. Сравнение строк напрямую не совпадёт.
2. Products, D25: после «Кроссовки «Азимут Бег»» есть пробел в конце. В Stock_Items (72–77) и Orders (16, 24) его нет.
3. Products, D27: полное название «Черные туфли в классическом стиле — база для деловых образов». В Stock_Items (81–83) и Orders (17) укорочено до «Черные туфли в классическом стиле». Это требует явного сопоставления, один strip не поможет. Сопоставлять также производителя «Барбари», а не только часть названия.
4. Sizes содержит и целые числа, и строки вроде `36.5`; половинные размеры в Stock_Items тоже встречаются строками. Привести значения к единому числовому виду, не округлять до целого.
5. Заголовок отчества в Users написан с опечаткой «Отчетсво». В имени Петрова в строке 3 используется латинская `e`: «Пeтр». Импорт по названию ожидаемого столбца может сломаться; произвольное исправление текстовых данных лучше не делать молча.
6. Products, строка 30: в поле «Производство» у мужских демисезонных ботинок «Барбари», а в описании написан «Берестов». Stock_Items и Orders используют «Барбари». Для связи брать структурированный столбец производства, а не вытаскивать производителя из описания.

Рекомендуемая подготовка: заменить неразрывные пробелы, нормализовать внешние/повторные пробелы в ключах; сделать явную карту одного укороченного названия; сопоставлять по модели И производству; проверить, что нормализация не склеила разные модели; логировать неизвестные ссылки и не пропускать строки молча. ## Модуль 2 — каталог и скидка

Приложение загружает модели из PostgreSQL, а не напрямую из Excel или захардкоженного списка. Главный экран показывает для каждой модели изображение, категорию, наименование, производство, состав, цену с учётом скидки и сумму доступного количества ПО ВСЕМ размерам.

Макет расположен на странице 15 PDF: вертикальный список карточек, слева изображение, сверху производство и название, в центральной части категория/количество/состав, справа цена. Приложение 3 содержит правила стиля, но самого графического макета в DOCX нет.

Стиль: Calibri; основной фон #FFFFFF; дополнительный #D2F6E7; акцент целевого действия #70B2AF; заголовок на каждом экране; логотип на главной форме с сохранением пропорций/цвета; иконка приложения при поддержке платформы; название приложения включает «Чудо Обувь».

Если изображения нет, оно недоступно или его невозможно загрузить, показывать picture.png. Проверять этот путь даже при том, что все 31 исходное изображение присутствуют. Использовать переносимые пути к ресурсам, включить файлы в проект.

Подсветка #ff8080 применяется, если общий остаток модели <= 3. При исходном импорте это ровно три модели: «Женские босоножки «Черный кофе» со скульптурным каблуком» — 3; «Туфли из натуральной кожи» (Берестов) — 3; «Ботинки мужские демисезонные» (Барбари) — 2. Например, две размерные позиции по 2 пары дают общий остаток 4 и подсветку не получают. После новых операций результат может измениться.

Скидка — 25% на модель, по которой не было ни одного заказа в предыдущем календарном месяце относительно даты расчёта. Проверять все размеры этой модели и связи order_items → orders. Предыдущий календарный месяц — не последние 30 дней. Удобная граница: от первого числа прошлого месяца включительно до первого числа текущего месяца исключительно. Январь должен корректно переходить к декабрю предыдущего года.

Цена со скидкой = базовая цена × 0.75; иначе базовая цена. Не менять базовую цену при каждом запуске и не применять скидку повторно к уже уменьшенной цене. Точность хранить в NUMERIC/Decimal.

На 11 октября 2026 года предыдущий месяц — сентябрь. В имеющихся исходных заказах нет сентября, поэтому все модели по правилу имеют скидку. Для ручной проверки удобно временно использовать отдельную копию БД/управляемую дату расчёта в мае или июне 2026 либо подготовить проверочные заказы. Нельзя молча менять системную дату или исходные материалы.

2.1: каталог, скидки, стиль, стабильный запуск, архив Module_2_Catalog.zip. 2.2: осмысленная структура папок и название, Автотест M2_PROJECT_STRUCTURE-XXXXXX. 2.3: именование кода, одна команда в строке, Автотест M2_CODE_STYLE-XXXXXX. На пробнике эти качества показывать вручную.

| Каталог | Да | Да | Да | Да |
| Поиск, фильтры, сортировка | Допустимо без них | Да | Да | Да |
| Оформление заказа, несколько позиций, изменение количества/удаление до подтверждения | Нет | Да | Да | Да |
| Общий список и состав заказов, добавление/удаление оформленных заказов | Нет | Не требуется | Да | Да |
| Редактирование уже оформленного заказа | Нет | Нет | Нет | Да |

Поиск — по названию И описанию, без учёта регистра. Модель подходит, если запрос найден хотя бы в одном из этих полей. Фильтр — по категории, значения из БД; первый пункт строго «Все категории». Сортировка цены по возрастанию/убыванию выбирается выпадающим списком. Всё работает сразу при изменении ввода, без кнопки «Найти». Фильтр и поиск совместны, выбранное направление сортировки сохраняется. Поиск не сбрасывать при выборе «Все категории» без отдельного требования. КИМ не уточняет, сортировать по базовой или фактической цене; разумно сортировать по показанной цене со скидкой и сохранить одно правило во всём интерфейсе.

При клике на карточку открываются актуальные данные модели: изображение, производство, наименование, категория, цена со скидкой, состав, описание, размерный ряд и доступные размеры. Размерный ряд и реально доступные размеры отличаются: наличие размера в общем справочнике не означает, что у выбранной модели есть доступные пары такого размера. Не приписывать модели весь справочник размеров автоматически.

Выбор количества: только положительное целое число, не больше доступного количества выбранного размера. Корзина поддерживает несколько разных моделей/размеров, изменение количества, удаление строки и полный отказ до подтверждения. При повторном добавлении одинаковой пары модель + размер учитывать уже находящееся в корзине количество.

При подтверждении сохранить пользователя, дату, все позиции, модель/размер/количество и цену за единицу НА МОМЕНТ оформления. Позднейшее изменение скидки/каталога не должно менять суммы старых заказов. Сумма = сумма количества × сохранённой цены.

Заказ и списание остатков сохранять одной транзакцией. Перед списанием снова проверять остаток; нельзя допускать частично сохранённый заказ или отрицательный остаток. До подтверждения корзина не должна необратимо менять БД. После успеха автоматически обновлять каталог и размеры без перезапуска приложения.

Сообщения об ошибках/предупреждениях/успехе должны иметь подходящие заголовки и пиктограммы; объяснять, что произошло и как исправить. Обрабатывать неверный логин, пустое/нечисловое/нулевое/отрицательное/дробное/слишком большое количество, недоступный размер, ошибку БД и файлов изображений. Не показывать traceback пользователю и не скрывать сбой пустым except. Параметризовать SQL — это техническая рекомендация для безопасной и корректной реализации.

3.1: функциональность и Module_3_Interface.zip. 3.2: сообщения, M3_FEEDBACK_MESSAGES-XXXXXX. 3.3: обработка ошибок, M3_ERROR_HANDLING-XXXXXX. 3.4: осмысленные комментарии к сложной логике, M3_CODE_COMMENTS-XXXXXX. Комментарии к каждой очевидной строчке не требуются.

## Модуль 4 — управление заказами и репозиторий

Для менеджера/администратора общий список заказов с датой и ФИО; переход к составу; возврат. В составе показывать модель (название и производство), размер, количество, историческую цену за единицу и итоговую сумму.

Менеджер и администратор добавляют новый заказ из каталога с поиском по названию, доступными размерами, количеством, несколькими позициями. Оба удаляют существующий заказ вместе с его позициями. Перед удалением нужна явная просьба подтвердить; отмена не меняет данные; после успеха/ошибки понятное сообщение; возврат к обновлённому списку.

Только администратор редактирует оформленный заказ: при открытии загрузить текущие дату и полный состав, разрешить изменение даты и удаление отдельных позиций, сохранить в БД. Функция изменения количества/добавления новых строк в уже подтверждённый заказ в модуле 4 прямо не требуется. Проверять право в операции, а не только скрывать кнопку.

Общий текст модуля 3 требует пересчитывать доступное количество при изменении информации о заказе. Поэтому при удалении заказа/позиции разумно возвращать количество на склад, а при добавлении списывать; делать это вместе с изменением заказа в одной транзакции. Если удаляется последняя позиция, поведение надо определить (например, запрет пустого заказа или удаление заказа с подтверждением): КИМ не задаёт точное правило. Изменение даты может изменить условие скидки, поэтому при возвращении в каталог данные должны быть актуальны.

После добавления, удаления, редактирования список заказов обновляется автоматически без перезапуска и ручного открытия формы заново.

В репозиторий исходники и ресурсы обычной структурой файлов, проект/конфигурацию, ERD в PDF, SQL-скрипт создания БД С ДАННЫМИ и README. На странице 25 дополнительно перечислены исполняемые файлы; для Python формат запуска/упаковки с преподавателями пока не согласован. Не объявлять EXE обязательным универсально и не считать один EXE достаточным. Указание `.dt` относится к 1С и для Python + PostgreSQL не применяется. В Git коммитить результаты и отправлять в предоставленный репозиторий; локальное сохранение файлов само по себе не означает загрузку.

README.md — именно в корне, UTF-8, Markdown. Обязательны: название с «Чудо Обувь»; язык/платформа или фреймворк/СУБД; назначение и каталог/оформление/управление заказами; подготовка БД и запуск. Для Python практически полезны requirements.txt и настройки подключения, которые позволяют преподавателю воспроизвести запуск. Архив проверять после распаковки в другую папку, чтобы поймать абсолютные пути и забытые ресурсы.

4.1: Module_4_Orders.zip. 4.2: файлы результатов в репозитории, M4_PROJECT_FILES-XXXXXX. 4.3: актуальная структура исходного кода и история, M4_SOURCE_CODE-XXXXXX. 4.4: README, M4_README-XXXXXX. Для Автотеста здесь выбирали бы локальную папку репозитория; на пробнике контрольных сумм не будет по договорённости пользователя.

## Модуль 5 — независимая аналитика

Нужны Sessions_analytics.csv, Orders_analytics.csv, Order_items_analytics.csv, Shoe_models_analytics.csv из приложения 4. Их в папке нет. Получить числовые ответы из текущих XLSX нельзя: там другой период, нет сессий/источников/устройств/status/discount_percent. Не подменять недостающий набор исходными заказами апреля–мая.

По умолчанию период 1 января — 31 марта 2026 года и завершённые заказы. В условиях используется и русское «завершён», и значение `completed`; реальную кодировку статуса проверять по CSV. Сессии для воронок/удержания нельзя оставлять только у покупателей: для знаменателя нужны все соответствующие посетители.

## Минимальный сценарий ручной демонстрации

1. Восстановить PostgreSQL из SQL с данными; показать семь сущностей, ключи, ограничения и ERD. Сверить исходные контрольные количества.

4. Войти `asidorova` (клиент): ФИО справа, одновременные поиск по описанию/названию, категория и сортировка; «Все категории» сбрасывает только фильтр.
5. Проверить неверный логин и количества 0, −1, дробь, буквы, больше остатка; показать полезные сообщения без аварии.
6. Оформить заказ с двумя моделями/размерами; проверить сохранённые строки и цены, списание соответствующих остатков и обновление каталога. Отменённая корзина не меняет БД. Новый номер после импорта не конфликтует.
